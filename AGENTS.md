# Agent guide

Conventions for working in this repository. The README explains _what_ the
project does; this file is about _how_ code must be written here. Follow it
over your defaults.

## Stack in one line

TanStack Start (React 19, SSR, Vite) · TanStack Router (file-based) ·
TanStack Query · Zod 4 · React Hook Form · shadcn/ui on Base UI + Tailwind 4 ·
Zustand · Logto (`@logto/browser`, SPA) · pnpm · ESLint · Prettier. Front-end
of `../nestjs12-boilerplate`, whose `AGENTS.md` describes the API side.

## Commands

```bash
pnpm dev                               # http://localhost:5173 (the API must run on :3000, Logto on :3001)
pnpm lint && pnpm typecheck && pnpm build   # must all pass before you are done
pnpm format                            # Prettier
pnpm exec shadcn add <component>       # into src/components/ui
```

There are no automated tests yet. Verify changes by building, then in the
browser: public pages are server-rendered, so check both the HTML and the
console (hydration errors). Pages behind sign-in need the seeded Logto
accounts of the API's README.

## Layout

```
src/
├── routes/                 # routing only (TanStack Router file routes)
├── features/<domain>/
│   ├── api/                # <domain>.keys.ts + one file per endpoint
│   ├── hooks/              # queryOptions + useX, mutation hooks
│   ├── components/
│   ├── schemas/            # Zod: API shapes, forms, search params
│   └── types/              # z.infer types, filters
├── components/
│   ├── ui/                 # shadcn, generated
│   ├── layout/             # app shell, navbar, user menu
│   └── common/             # generic pieces: page header, pager, states
├── lib/
│   ├── api/                # HTTP client + ApiError
│   ├── auth/               # AuthClient; the only place that knows Logto
│   ├── query/              # createQueryClient
│   ├── utils/
│   └── env.ts              # Zod-validated import.meta.env
├── stores/                 # Zustand, client state only
├── types/                  # truly global types (router context, pagination)
├── router.tsx              # getRouter(): QueryClient, context, SSR integration
└── routeTree.gen.ts        # generated by the router plugin, never edited
```

`posts` is the reference feature: copy its shape, don't invent one. Only
create the subfolders a feature needs.

## Routes

- One page = one folder: `login/index.tsx`, `blog/$postId/index.tsx`. No
  `login.tsx` or `blog.$postId.tsx`. A folder's `route.tsx` is its layout or
  guard.
- A route declares, and only declares: `validateSearch`, `beforeLoad`,
  `loaderDeps`, `loader`, `head`, `ssr`, and a page component that reads
  params/search/context, calls feature hooks and composes feature
  components. No business logic, no JSX beyond composition.
- Data: the loader warms the cache with the feature's queryOptions, the
  component reads the same queryOptions through the feature's hook:

  ```tsx
  loaderDeps: ({ search }) => ({ page: search.page }),
  loader: ({ context, deps }) =>
    context.queryClient.ensureQueryData(postsQueryOptions(deps)),
  // component: const { data: posts } = usePosts({ page })
  ```

- URL state (page, filters, sort) goes through `validateSearch` with a Zod
  schema whose fields have `.default()` / `.catch()`, so a bad URL is
  normalized instead of crashing. Shared: `pageSearchSchema`.
- Map API 400/404 to `throw notFound()` in the loader (`isApiError`), let
  anything else reach `RouteError`.
- The router defaults (`router.tsx`) provide the pending, error and
  not-found components; don't repeat them per route.

## Auth and guards

- Logto owns sign-in, sign-up, passwords and MFA on its hosted pages:
  `/login` and `/register` only send the user there (`AuthPanel`), and
  `/callback` finishes the flow. There is no login form in the app.
- Only `src/lib/auth/logto-auth-client.ts` imports `@logto/*` (ESLint
  enforces it). The app talks to the `AuthClient` interface
  (`lib/auth/auth-client.ts`); `lib/auth/auth.ts` picks the implementation.
  Components get it with `useAuthClient()`, guards with `context.auth`.
- The signed-in user is `{ id, roles }` read from the API's access token,
  the same claims the API checks. It lives in TanStack Query
  (`authUserQueryOptions`), shared by guards and UI. In components use
  `useAuthUser()`: `undefined` until hydrated, then `null` or the user.
- Roles: `USER_ROLES` mirrors the API's `UserRoleEnum`. The `roles` claim
  exists because the API's `pnpm seed` installs a Custom JWT script in Logto.
  New role: add it on the API first, then to `USER_ROLES`.
- Tokens live in the browser, so every route that depends on the session is
  `ssr: false`. On the server, `getUser()` is always `null` and API calls
  go out without a token.
- `_protected/route.tsx` is the only authentication guard. Signed out →
  `redirect` to `/login?redirect=<href>`, then back after sign-in.
  It returns `{ user }`, typed in the context of every child route.
- `_protected/admin/route.tsx` adds the role check. Signed in without the
  role → `throw notFound()`, like the API answers 404 rather than 403.
- A frontend guard is UX only: the route tree ships in the bundle, and the
  API authorizes every request itself. Never rely on a guard to protect
  data.
- `?redirect` values must pass `authSearchSchema` (same-site paths only):
  never redirect to a URL coming from the query string without it.

## Server state: TanStack Query

- Everything coming from the API lives in TanStack Query. Never copy it into
  Zustand, context or `useState`.
- Per feature:
  - `api/<domain>.keys.ts`: key factory (`all`, `lists()`, `list(filters)`,
    `details()`, `detail(id)`). No hand-written key arrays elsewhere.
  - `api/<verb>-<thing>.ts`: one function per endpoint, through `api`.
  - `hooks/use-<thing>.ts`: `xQueryOptions(...)` (used by loaders) and
    `useX(...)`. Pass `signal` from the query function to the API call.
- Reads preloaded by a loader use `useSuspenseQuery`: `data` is always
  defined. A component outside a loader (navbar) uses `useQuery` with the
  same queryOptions and handles `undefined`.
- Mutation hooks update the cache in `onSuccess`: `setQueryData` when the API
  returns the updated resource, `invalidateQueries` on the lists otherwise.
  Return that promise so the mutation stays pending until the cache is fresh.
- One QueryClient per request on the server, one in the browser:
  `createQueryClient()` in `getRouter()` only. `setupRouterSsrQueryIntegration`
  dehydrates what loaders fetched and hydrates it in the browser.

## HTTP client

- `lib/api/client.ts` knows HTTP only: base URL, Bearer token from
  `authClient`, JSON or `FormData` bodies, query strings, errors. No endpoint
  and no business rule in it. Never call `fetch` elsewhere.
- `api.get(path, { schema, query, signal })`: with a `schema` the response is
  validated and typed; without one it resolves to `void` (204).
- Errors are `ApiError`: `status` and `code`, the API's `UPPER_SNAKE` message
  (`POST_NOT_FOUND`, `NOT_POST_AUTHOR`…). Match on `code`; display with
  `getErrorMessage()`. Queries don't retry 4xx.

## Validation and typing: Zod everywhere

- Response schemas mirror the API's response DTOs (`GetPostDto` →
  `postSchema`), field for field. When the API changes a DTO, change the
  schema in the same pass.
- Form schemas copy the API's request rules (lengths, trims, file types and
  sizes) with user-facing messages. The API validates again; the form
  schema is for UX.
- Search params, env vars (`lib/env.ts`), token claims: Zod too.
- Types are inferred (`z.infer` / `z.output` in `types/`); don't hand-write a
  type that duplicates a schema. No `any`: take `unknown` and parse it.
- Env: add the variable to `lib/env.ts` and `.env.development`. Every `VITE_`
  variable is public (it ships in the bundle): no secrets. Local overrides go
  to `.env.development.local` (gitignored). Values are inlined at build time
  and `pnpm build` doesn't read `.env.development`: to run a build locally,
  `pnpm build --mode development && pnpm preview`.

## Forms

React Hook Form + `zodResolver` + shadcn `Field`, one `Controller` per field:

```tsx
<Controller
  name="title"
  control={form.control}
  render={({ field, fieldState }) => (
    <Field data-invalid={fieldState.invalid}>
      <FieldLabel htmlFor={field.name}>Title</FieldLabel>
      <Input {...field} id={field.name} aria-invalid={fieldState.invalid} />
      <FieldError errors={[fieldState.error]} />
    </Field>
  )}
/>
```

Submit through the feature's mutation hook; show `mutation.error` with
`getErrorMessage()`. File inputs: don't spread `field` (no `value`), pass
`event.target.files?.[0]` to `onChange`, and reset the `<form>` element after
upload (see `ProfilePictureForm`).

## Client state: Zustand

- `stores/` only holds state that exists in the browser alone: UI state
  (`ui.store.ts`: mobile menu) and preferences (`preferences.store.ts`:
  theme). Never API data, never URL state.
- A persisted store uses `skipHydration: true` and is rehydrated after
  mount, otherwise the first render doesn't match the server HTML.
- What must be right at the first paint can't wait for that: the theme is
  applied by `ThemeScript`, an inline `<head>` script (`ScriptOnce`) that
  reads the persisted preference before the body renders. `applyTheme` is
  serialized into it, so it must stay self-contained.

## Components

- `components/ui`: generated by `pnpm exec shadcn add`, never edited by hand
  and excluded from ESLint. They are built on Base UI: compose with the
  `render` prop (`<DropdownMenuItem render={<Link to="/profile" />}>`), not
  `asChild`. For a link styled as a button, use
  `className={buttonVariants(...)}` on the `Link`.
- `components/layout` and `components/common`: shared, no domain knowledge
  beyond composing features (the user menu composes auth and profile).
- Anything tied to a domain goes in `features/<domain>/components`.
- SSR: never read `window`, `localStorage` or the session during render.
  UI that depends on the browser waits for `useHydrated()` (TanStack Router).

## Imports

- Always `@/…`, never deep relative paths. No `index.ts` barrels: import the
  file that defines the thing (`@/features/posts/hooks/use-posts`).
- A feature may import another feature's files (`profile` uses `users`'
  schema and avatar) in one direction only. `import/no-cycle` is on and
  `pnpm lint` fails on a cycle.
- Type-only imports use a top-level `import type`.

## Style

- Comments only for genuine gotchas (security, SSR/hydration, library
  quirks, contracts with the API or Logto). No JSDoc on ordinary code, no
  "what this does" comments.
- Files are `kebab-case` with a role suffix where it helps: `.schema.ts`,
  `.types.ts`, `.keys.ts`, `.store.ts`; hooks are `use-x.ts`; components are
  `x.tsx` exporting `PascalCase`; constants `UPPER_SNAKE`.
- Prettier decides formatting (no semicolons, double quotes).
- Update the README when routes, env vars or setup change.

## Recipes

**New feature** (e.g. `comments`, once the API has the endpoints):
`schemas/comment.schema.ts` (mirror of the DTOs) → `types/comment.types.ts`
→ `api/comment.keys.ts` + `api/get-comments.ts` → `hooks/use-comments.ts`
(`commentsQueryOptions`, `useComments`) → mutation hooks → components.

**New signed-in page**: `src/routes/_protected/settings/index.tsx` with
`createFileRoute("/_protected/settings/")` serves `/settings`, behind the
guard, with `Route.useRouteContext().user` typed.

**New admin page**: `src/routes/_protected/admin/reports/index.tsx` serves
`/admin/reports`, behind both guards.

## Do not

- Put API data in a store, or call `fetch` outside `lib/api/client.ts`.
- Import `@logto/*` outside `src/lib/auth`, or store tokens yourself.
- Add `index.ts` barrels, or put business logic in `routes/`.
- Treat a route guard as security.
- Edit `src/routeTree.gen.ts` or `src/components/ui/*` by hand.
- Use `any`, or put secrets in `VITE_` variables.
- Bypass pnpm's `minimumReleaseAge` policy (no `minimumReleaseAgeExclude`
  entries to get a package published hours ago).
